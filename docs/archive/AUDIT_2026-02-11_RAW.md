## 1. Vue d'ensemble de l'application

### Description

Application React/TypeScript de gestion de fiches de personnage pour JdR (jeux de rôle). Elle comprend :

- **App principale** : Fiche de personnage interactive (attributs, compétences, combat, journal de campagne)
- **App admin** : Interface d'administration pour gérer les règles, bibliothèques et campagnes
- **Backend** : Supabase (BDD PostgreSQL, Auth, Storage)
- **Déploiement** : GitHub Actions (CI/CD)

### Stack technique

| Couche | Technologie |
|--------|------------|
| Framework | React 18 + TypeScript |
| Build | Vite 5 (dual build : main + admin) |
| Styling | Tailwind CSS 3.4 |
| State | React Context API (CharacterContext, RulesContext, NotificationContext) |
| Validation | Zod 4 |
| Backend | Supabase (Auth + PostgreSQL + Realtime) |
| Rich Text | TipTap 3 |
| Compression | pako (gzip) |
| Storage local | IndexedDB (idb-keyval) |
| Tests | Vitest + Playwright |
| Icons | Lucide React |

## 2. Architecture & Structure

### Flow de données

```
Supabase DB
    ↓
RulesLoader (multi-source: Supabase → GitHub API → CDN fallback)
    ↓
RulesContext (cache + état global des règles)
    ↓
CharacterContext (état du personnage + localStorage)
    ↓
CharacterSheet → Sections (Attributes, Skills, Combat, Counters)
    ↓
Modifications utilisateur → CharacterContext.onChange()
    ↓
CharacterSyncService → Supabase (upload compressé)
```

### Authentification

```
AdminApp → supabase.auth.getSession()
    ├── Session trouvée → AdminDashboard (accès complet)
    └── Pas de session → LoginScreen (email/password)
        ↓
        supabase.auth.signInWithPassword()
        ↓
        onAuthStateChange → met à jour session
```

### Système de migration

```
Donnée brute (localStorage / Supabase)
    ↓
migrateData() → Check _schemaVersion
    ↓
v0 → v1 : 9 migrations séquentielles
    ├── migrateTerminology (vertu→avantage, defaut→desavantage)
    ├── migrateTraits
    ├── migrateCounters
    ├── migrateAttributes
    ├── migrateNotebook
    ├── migrateLibrary
    ├── migrateSpecializations
    ├── migrateSkills
    └── migrateDefaults
    ↓
Validation Zod (CharacterSheetDataSchema)
    ↓
Donnée migrée et validée
```

## 3. Issues Critiques

### 3.1 `playwright` dans les dependencies de production

**Fichier** : [package.json:27](package.json#L27)
**Sévérité** : CRITIQUE

```json
"dependencies": {
    "playwright": "^1.58.2"   // ❌ ~100-150 MB en production
}
```

Playwright est un framework de test qui n'a rien à faire dans les dépendances de production. Il gonfle inutilement le `node_modules` et potentiellement le bundle.

**Fix** : Déplacer vers `devDependencies`.

---

### 3.2 Catch vide - Perte silencieuse de données

**Fichier** : [src/components/RulesSourceSelector.tsx](src/components/RulesSourceSelector.tsx) (~ligne 33)
**Sévérité** : CRITIQUE

```typescript
try {
    const parsed = JSON.parse(saved);
    // ...
} catch (e) { }  // ❌ Erreur avalée silencieusement
```

Si le JSON en localStorage est corrompu, l'utilisateur perd sa session sans aucun message. L'application ne restaure pas les données et ne prévient pas.

**Fix** : Logger l'erreur via ErrorService, afficher un message utilisateur.

---

### 3.3 `Promise.all` sans gestion d'erreur dans LibraryLoader

**Fichier** : [src/services/library/LibraryLoader.ts](src/services/library/LibraryLoader.ts) (~ligne 18)
**Sévérité** : CRITIQUE

```typescript
const [traits, skills, specs, ...] = await Promise.all([
    DatabaseService.fetchAll<any>('libraries_traits', ...),
    DatabaseService.fetchAll<any>('libraries_skills', ...),
    // 12 requêtes simultanées sans try/catch
]);
```

Si UNE SEULE requête échoue, tout le `Promise.all` rejette → crash du chargement des bibliothèques.

**Fix** : Envelopper dans try/catch, utiliser `Promise.allSettled()`, ou retourner des valeurs par défaut en cas d'erreur.

---

### 3.4 Suppression en cascade sans transaction

**Fichier** : [src/services/CampaignService.ts](src/services/CampaignService.ts) (~ligne 260)
**Sévérité** : CRITIQUE

```typescript
async deleteSetting(id: string): Promise<boolean> {
    await Promise.all([
        DatabaseService.deleteBy('libraries_traits', ...),
        DatabaseService.deleteBy('libraries_skills', ...),
        // ... 6+ suppressions parallèles sans transaction
    ]);
}
```

Si une suppression échoue et les autres réussissent → base de données dans un état incohérent (données orphelines).

**Fix** : Utiliser `Promise.allSettled()`, vérifier les résultats, ou implémenter une transaction côté Supabase (RPC).

---

### 3.5 Validation Zod ignorée après échec

**Fichier** : [src/services/CampaignService.ts](src/services/CampaignService.ts) (~ligne 138)
**Sévérité** : CRITIQUE

```typescript
const validationResult = RulesDataSchema.safeParse(rulesRaw);

if (!validationResult.success) {
    console.warn("[CampaignService] Validation Details:", ...);
    // ⚠️ Continue quand même !
}

const rules = rulesRaw as RulesData;  // ❌ Cast malgré validation échouée
```

Des données invalides sont utilisées comme si elles étaient valides → comportements imprévisibles, crashes potentiels.

**Fix** : Retourner `null` si la validation échoue, ou utiliser `validationResult.data` uniquement en cas de succès.

---

### 3.6 Migrations silencieuses en cas d'erreur

**Fichier** : [src/utils/migrations/index.ts](src/utils/migrations/index.ts)
**Sévérité** : CRITIQUE

```typescript
steps.forEach(step => {
    try {
        step(migrated);
    } catch (e) {
        console.error(`[Migration] Failed...`, e);
        // ❌ Continue malgré l'erreur
        // ❌ Version mise à jour quand même → migration jamais retentée
    }
});
migrated._schemaVersion = CURRENT_SCHEMA_VERSION;  // Marqué comme migré !
```

**Scénario catastrophe** :
1. Étape 2 échoue → données partiellement migrées
2. Version marquée v1 → prochaine session, migration pas retentée
3. Corruption permanente et silencieuse

**Fix** : Tracker les échecs, ne pas mettre à jour `_schemaVersion` si des étapes échouent, deep copy avant migration.

---

### 3.7 Shallow copy dans les migrations

**Fichier** : [src/utils/migrations/index.ts](src/utils/migrations/index.ts) (~ligne 23)
**Sévérité** : CRITIQUE

```typescript
let migrated = { ...parsed };  // ❌ Copie superficielle
```

Les objets imbriqués (attributes, skills, etc.) sont des **références partagées**. Si la migration échoue à mi-chemin, les données originales sont aussi corrompues.

**Fix** : `let migrated = JSON.parse(JSON.stringify(parsed));` (deep copy).

---

### 3.8 Pas de validation de rôle dans l'admin

**Fichier** : [src/admin/AdminApp.tsx](src/admin/AdminApp.tsx)
**Sévérité** : CRITIQUE

```typescript
if (!session) {
    return <LoginScreen />;
}
// ❌ Si session existe → accès admin complet
// ❌ Pas de vérification de rôle
```

N'importe quel utilisateur authentifié Supabase a accès à l'interface admin complète. La sécurité repose **entièrement** sur les politiques RLS de Supabase, qui ne sont documentées nulle part dans le code.

**Fix** : Ajouter une vérification de rôle côté frontend ET documenter les politiques RLS.
